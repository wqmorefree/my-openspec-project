# ADR-005：数据模型——sys_asset 主表 + 子表独立 change

## 状态
已采纳

## 背景
资产数据含 12 大类 Tab：既有「基础信息」主数据，也有大量子表（部署信息、接口依赖、数据库等）。change 需定义主表承载「基础信息」，同时为 11 个后续子表 Tab 预留扩展点，使各 Tab 可独立交付。

## 选项

| 选型 | 优点 | 缺点 |
|------|------|------|
| 一表全装（单表覆盖所有 Tab） | 表少、查询简单 | 字段冗余大、与 Tab 边界不符；后续新增 Tab 都要改主表结构，扩展困难 |
| 主表 + 子表逐 change 建表 | 每个 Tab 独立演进、边界清晰；主表可独立先行交付 | 表数量多；删除系统需处理级联 |

## 决策
选择"主表 + 子表独立 change 建表"：change 1 仅建 `sys_asset` 主表，后续每个子表 Tab 各自 change 建 `sys_asset_*` 表。删除采用**逻辑删除**（`is_deleted` 置 1 + `deleted_time`），记录保留在库内。

## 理由
- 与"每个 Tab 一个 change"的拆分策略解耦，主表（基础信息）可独立交付验收，不阻塞首个纵向切片。
- 字段归属清晰：主表只含基础信息字段 + 通用审计列，子表按业务域（部署/接口/数据库等）各自成型，避免单表字段膨胀。
- `code` 建部分唯一索引 `WHERE is_deleted=0`，既保证唯一性硬约束，又兼容软删除（已删记录不占唯一名额）。
- 删除采用逻辑删除：记录不再出现于任何列表、但数据保留，为后续审计留痕提供天然取证源，避免"物理删除后删除动作不可追溯"的张力；删除事件在审计 change 中可作为更新快照追溯。
- 为何不用物理删除：物理删除会永久抹除记录，一旦需要审计"删前快照"即无源可取，也无法支持误删恢复。
- 删除系统时连带逻辑删除子表作为预留钩子先行设计，子表建成后主表删除逻辑无需重构。
- 代价是表数量多、关系管理要求高，逻辑删除会积累历史数据（本项目内部台账量小，可接受），但在拟定的变更拆分节奏下可控。
