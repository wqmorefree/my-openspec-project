# `tasks.md` 编写规范 (SDD 标准版)

## 1. 文件基本结构
一份优秀的 `tasks.md` 文件应包含三个核心层次，确保任务有全局上下文、清晰的执行细节以及正确的执行顺序。

### 第一层：任务元信息
位于文件顶部，提供项目的整体背景和总控信息。
*   **项目名称**：标识所属项目。
*   **关联文档**：链接到相关的 `design.md` 或需求文档。
*   **任务总数**：统计总任务量。
*   **执行策略**：说明整体推进方式（如：按依赖顺序执行、可并行执行的任务等）。

### 第二层：任务列表
文件的主体部分，按顺序列出每个具体任务。

### 第三层：执行顺序
位于文件底部或作为独立模块，梳理任务之间的依赖关系。
*   **任务依赖关系图**：用图表或缩进列表展示任务的先后依赖。
*   **推荐执行顺序**：给出建议的执行路径。

---

## 2. 任务粒度标准 (Task Granularity)
任务拆解的难点在于“每个任务多大”，粒度过粗或过细都会导致管理或执行成本过高。

*   **太粗（例如：实现整个采集层）**：AI 上下文窗口不够，容易中途“忘记”接口契约或数据模型，导致代码与 `design.md` 南辕北辙。人类虽然可应对，但容易偏离设计。
*   **太细（例如：给函数添加一个参数）**：任务数量急剧增长，管理成本远超执行成本，缺乏完整性。
*   **✅ 最佳区间**：任务颗粒度应控制在一个**可测试的交付物**。
    *   **代码量**：一个任务的代码量为 **50~200 行**。
    *   **执行时间**：一个任务的执行时间为 **10~30 分钟**。
    *   **交付物**：一个任务产出一个可测试、可验证的交付物。

## 3. 单个任务模板格式
每个任务必须遵循统一的模板格式，以便于结构化管理和自动化测试。

```markdown
## Task N: [任务标题]  <!-- 标题须用动词开头，如：实现、创建、集成 -->

**描述**：用1到2句话说明这个任务做什么。 <!-- 只说“做什么”，不说“怎么做”（留给 AI 实现细节） -->

**输入**：需要哪些前置任务的产出作为输入。

**输出**：这个任务完成后产出什么文件或模块。

**依赖**：Task X, Task Y (必须优先完成的任务)。

**验收标准**：
- [ ] 具体的、可执行的、二值化的验收条件1
- [ ] 具体的、可执行的、二值化的验收条件2
- [ ] ......

**设计原则**：
- 标题用动词开头。
- 描述只讲目标，不讲实现路径。
- 验收标准可直接转化为测试用例。
```

## 4. 核心规范：优秀的验收标准 (Acceptance Criteria)
验收标准是任务完成与否的唯一判定依据。SDD 规范要求验收标准必须具备三个核心特征：**可执行、可观测、二值化**。

### 4.1 三大特征
*   **可执行**：可以通过运行代码或测试来验证，不需要人工进行主观判断。
*   **可观测**：验证结果是清晰可见的，例如测试通过、输出正确、日志符合特定格式等。
*   **二值化**：结果只有“通过”和“不通过”两种状态，不存在“差不多通过”的模糊地带。

### 4.2 验收标准对比 (优秀 vs 低劣)

#### 可执行案例：
*   **低劣**：代码质量好（模糊、不可执行）
*   **优秀**：`pylint 评分 >= 8.0`（执行一下就知道）

#### 可观测案例：
*   **低劣**：能正常获取数据（模糊、不可观测）
*   **优秀**：`mock GitHub API返回3条commit，collect()返回3个CommitRecord，字段类型正确`（通过测试就能验证）

#### 二值化案例：
*   **低劣**：错误处理完善（不可二值化）
*   **优秀**：`API超时时重试3次并返回空列表+错误日志`（通过/不通过）


### 💡 核心原则
**能写成自动化测试的验收标准，就是好的验收标准。** 优秀的验收标准本质上就是一份可执行的测试清单。
