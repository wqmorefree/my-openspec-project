# change 的 design.md 编写规则

> 适用场景：创建或修改 `openspec/changes/*/design.md` 时。
> 关联索引：AGENTS.md 6.2 协同规则第 5 条；ADR 规则见 `docs/rules/adr.md`。

## 一、固定六章结构

所有 change 的 `design.md` 必须按以下章节生成，**不得增删章节**：

```markdown
## 系统架构       # 架构图 + 模块间关系/通信 + 数据流向
## 模块职责       # 涉及的工程模块及各模块职责表
## 数据模型       # 建表 SQL / 字段规范说明（遵循 docs/rules/database.md）
## 接口契约       # 通用约定 + 关键端点（草案）表
## 技术选型（ADR） # 仅 ADR 引用清单，格式 `ADR-NNN -> 短名`，不写决策细节
## 非功能性约束   # 安全 / 性能 / 可运维性 / 错误处理
```

## 二、写作要求

- **系统架构**：放架构图（文本/代码块均可）+ 模块间关系与通信（含认证链路、连接方式）+ 数据流向（查询/写入/导入/导出至少覆盖变更涉及的主流程）。
- **模块职责**：表格列出涉及的工程模块与其职责、本 change 内交付或改动点。
- **数据模型**：变更涉及的建表 SQL 或字段规范说明，遵循 `docs/rules/database.md`；注明主键策略、通用字段、唯一索引约束。
- **接口契约**：先写通用约定（前缀、响应体 R<T>、分页格式、鉴权、错误码），再列关键端点表（口径草案）——Method / Path / 说明 / 权限。
- **技术选型（ADR）**：**仅引用清单**，格式 `ADR-NNN -> 语义短名`，不写决策细节、不放链接。决策内容全部在 `docs/adr/`。
- **非功能性约束**：按 安全 / 性能 / 可运维性 / 错误处理 四个子节组织。

## 三、禁止事项

- **不写 Context**：proposal 的 Why 已覆盖，design.md 不再重复背景。
- **不设 Risks / Migration / Open Questions 尾段**：选项与理由进 ADR，实施顺序进 tasks.md。
- **遗留风险以普通条目陈述**：直接在所属子节（如可运维性、安全）用一句"风险 + 要求"写明问题与处理要求，**禁止自创词汇**（如"跨章风险"）。
- 结构标题英文固定，内容中文。

## 四、调用时机

- `/opsx-propose` 生成提案时，按本结构产出 design.md。
- 凡改动 design.md 章节必须维持六章结构，不得增删章节名。
